## 1. Зачем

Этап 31 закончился выводом «узкое место — лексическое покрытие, а не декодер», и в README висит
задача 1 с критерием «доля фраз SP-10, доходящих до оценки, выше 40%». Но цена закрытия разрыва
не была измерена: сколько классов надо добавить, чтобы закрыть 40%, и сколько из них вообще чем-то
обучаются. Без этого «расширять словарь» — работа без плана.

Что входит в этап: инструмент, который считает разрыв и цену класса; канонизация, которая
закрывает часть разрыва без новых данных; пересчёт декодера на выросшей выборке; дефект,
найденный по дороге. Что не входит: само обучение расширенной головы (следующий этап, список
классов для него приложен).

## 2. Инструмент

`tools/vocab_gap.py` — ничего не качает и не обучает, только считает по инвентарям и checkpoint:

```
python tools/vocab_gap.py --benchmark D:/hfdata/sp10_eval.json --list классы.json
```

Гейт тот же, что у оценки: фраза доходит до замера, если после канонизации **каждое** её слово
есть среди имён классов головы (и клип лежит в кэше ландмарок). Дальше — жадная кривая:
классы упорядочены по числу блокируемых фраз, фраза разблокирована, когда добавлен её самый
«поздний» класс.

## 4. Почему лемма, а не срез окончания

Этап 20 ввёл `canon_map`: «автомобилем» → «автомобиль», потому что знак не склоняется. Реализация
срезала окончание по списку и требовала, чтобы корень был не короче 4 символов. Это правило
молча отсекает короткие слова — а в русском их большинство: `дома` не сворачивается в `дом`
(корень 3 символа), `мне`, `него`, `туда` в похожей ситуации. Нормальная лемма (`pymorphy3`,
MIT, уже стоял в venv) добирает именно их: в dev+test — 104 словоформы, в train — 194.

Правило неоднозначности сохранено, а не ослаблено: лемма, которая указывает сразу на два имени
класса, не маппится вовсе (`lemma_index`), так что метка не может оказаться чужой.

Что в коде: `canon_map(plain, vocab, morph=None)` — третий аргумент, поведение по умолчанию
прежнее; `load_morph()` — ленивый импорт, чтобы пути без `--lemma` работали и без пакета;
флаги `--lemma` в `tools/sweep_decode.py` и `tools/finetune_ctc_phrases.py`; `pymorphy3>=2.0` в
`requirements.txt` (CI на ubuntu поставит его, тест гоняет настоящую морфологию).

## 5. Дефект B70: два разных словаря головы в одном замере

Нашлся при сверке: `vocab_gap` насчитал 111 оцениваемых фраз, `sweep_decode` прогнал 112 клипов.
Разница не в данных, а в том, что канонизация строила словарь головы как
`{n.lower() for n in names}`, а гейт меток — через `class_index(names)`, который режет синонимы
«а/б» и нормализует «ё»→«е». Итог: класс `всё` искали как `всё` там и как `все` тут, форма
`нее` попадала в класс только с одной стороны, и набор фраз в оценке зависел от того, какой из
двух словарей спросить.

Починено в одном месте, а не по вызовам: `class_index` теперь заводит ключ и в нормализованном,
и в исходном виде (поэтому корпусные глоссы с «ё» перестали теряться — корпусная LM недосчитывалась
22 фраз из 2512), а все пять мест канонизации (`sweep_decode`, `finetune_ctc_phrases`,
`finetune_dict`, `rerank_eval`, `vocab_gap`) берут словарь через `head_names(names)` — ровно тот
же, что у гейта. Проверка: `tests/test_vocab_gap.py::test_class_index_reads_both_yo_forms`.

## 6. Декодер пересчитан на выросшей выборке: B67 становится различимым

Этап 31 замерял декодер на 59 клипах и честно написал «ни один кандидат не отличим от
production по бутстрапу». После леммы оцениваемых фраз стало 111 (×1,9), и вывод поменялся.

Протокол, чтобы не подбирать по тесту: конфиг замораживается по канонизированному F1 на
train-сплите SP-10 (`--tune`, 252 клипа), отчёт — по dev+test (111 клипов) и по независимому
Rutube-каналу (67 клипов). Freeze дал `none / lm 0 / wb 4 / sm3 / beam24`; прогон и сравнение —
с лемменной канонизацией (`sweep_decode --lemma`). Файлы: `reports/evidence/stage32_decoder_sweep.json`,
`reports/evidence/stage32_decoder_boot.json`.

| Набор | Метрика | Кандидат (заморожен) | Production (`corpus/0.1/wb2/sm1`) |
|---|---|---|---|
| SP-10 train, 252 клипа | попаданий слом → сущ. слов | 46 → **61** | 20 → **27** |
| | пустых фраз | **1,2 %** | 38,5 % |
| | средний F1 | **0,0712** | 0,0572 |
| SP-10 dev+test, 111 клип | попаданий | **19** | 8 |
| | recall / precision (сущ.) | **0,054** / 0,049 | 0,023 / **0,116** |
| | пустых фраз | **0,9 %** | 45 % |
| Rutube-канал, 67 клипов | попаданий | **57** | 32 |
| | recall (сущ.) | **0,291** | 0,163 |
| | пустых | **0 %** | 10,4 % |

Парный бутстрап по клипам (`hits_canon`, 4000 ресемплов, seed 2026), кандидат против production:

| Набор | Δ попаданий/клип | 95 % ЦИ | побед кандидата / production | различимы |
|---|---|---|---|---|
| SP-10 train | +0,135 | [0,091; 0,179] | 35 / 1 | да |
| SP-10 dev+test | **+0,099** | **[0,045; 0,162]** | 11 / 0 | **да** |
| Rutube-канал | +0,373 | [0,239; 0,522] | 22 / 0 | да |

Три независимых набора, один и тот же знак, ЦИ без нуля. Вывод этапа 31 был артефактом
объёма выборки, а не свойств декодера (в §4.2 отчёта 31 на это указал сам замер).

Внутри сетки вывод, наоборот, остался: `none/wb4/sm3` против `none/wb4/sm1` на dev+test —
ЦИ [0,000; 0,027] содержит 0, различия не видно (на train видно: +0,070, ЦИ [0,036; 0,103]).
Расширение выборки сделало различимым разрыв «production против всех» и не сделало различимым
порядок внутри верхушки сетки.

Что кандидат делает на самом деле: он почти не фильтрует. `lm_src=none` + `wb4` + `sm3` выдают
в 5,6 раза больше глоссов на клип (3,5 против 0,62 на eval), поэтому пустых фраз 0,9 % вместо
45 %, а precision падает вдвое (0,049 против 0,116). Это размен recall на precision, а не
«лучшее распознавание»: для глухого пользователя пустой экран хуже лишнего слова, но решение
о дефолтах в трёх местах (`dialogue_translator`, `check_translation`, `eval_phrase_clips`) —
за Вадимом, и молча их не трогали. Честно сказать и про проигрыш: на dev+test по F1 первое
место у `none/wb4/sm1` (0,0643 против 0,0513) — он точнее, но меньше ловит; замороженный по
train кандидат выбран заранее, и по нему, а не по красивому числу с теста, и стоит судить.
